# 🔒 5.2 -- TLS in Kubernetes

Welcome to the practical application of TLS within a Kubernetes cluster. Now that we understand the basics of Public Key Infrastructure (PKI), we will explore exactly how these certificates are deployed to secure a production-grade Kubernetes environment.

---

## 📌 Overview

Securing a Kubernetes cluster requires a complex web of encrypted communications. Whether you are an administrator using `kubectl` or an internal system component, every interaction must be authenticated and encrypted.

To achieve this, Kubernetes uses two primary types of certificates:
1.  **Server Certificates:** Used by components that *provide* a service (e.g., the API Server).
2.  **Client Certificates:** Used by components that *consume* a service (e.g., the Scheduler).

### 💡 Quick Reminder: Naming Conventions
Before diving in, remember the standard file extensions:
*   **Public Certificates:** `.crt` or `.pem` (e.g., `server.crt`)
*   **Private Keys:** `.key` or contains "key" in the name (e.g., `server.key`)

## 🖥️ Server Certificates

Server certificates are deployed on components that expose an HTTPS endpoint. Their job is to prove the server's identity to any client attempting to connect.

### Key Server Components:

| Component | Certificate & Key | Role |
| :--- | :--- | :--- |
| **Kube API Server** | `api-server.crt` / `api-server.key` | Provides the main HTTPS entry point for the entire cluster. |
| **etcd Server** | `etcd-server.crt` / `etcd-server.key` | Secures the cluster's primary data store. |
| **Kubelet** | `kubelet.crt` / `kubelet.key` | Secures the HTTPS API endpoint on every worker node. |

## 👤 Client Certificates

Client certificates are used for **Authentication**. When a client component connects to the API server, it presents its certificate to prove who it is.

### Key Client Components:

*   **Admin User:** Uses `admin.crt` and `admin.key` via `kubectl` to perform cluster management.
*   **Kube Scheduler:** Uses `scheduler.crt` and `scheduler.key` to authenticate with the API server to schedule pods.
*   **Kube Controller Manager:** Uses its own cert/key pair to manage cluster state and controllers.
*   **Kube Proxy:** Uses `kube-proxy.crt` and `kube-proxy.key` to manage network rules on worker nodes.

> [!NOTE]
> **Dual Roles:** Some components act as both. For example, the **Kube API Server** is a server to the admin, but it acts as a **client** when it communicates with the **etcd server**. In this case, it uses a client certificate to authenticate itself to etcd.

## 📊 Grouping the Certificates

To simplify your mental model for the CKS exam, group the certificates as follows:

| Certificate Group | Who uses it? | Purpose |
| :--- | :--- | :--- |
| **Client Certificates** | Admin, Scheduler, Controller-Manager, Kube-Proxy | To access the Kube API Server. |
| **Server Certificates** | Kube API Server, etcd Server, Kubelet | To authenticate incoming client connections. |

---

## 🏛️ The Root of Trust: The Certificate Authority (CA)

All the certificates mentioned above—whether client or server—must be signed by a trusted **Certificate Authority (CA)**. Without a CA signature, the components will not trust each other.

In most Kubernetes deployments, there is one primary CA:
*   **CA Certificate:** `CA.crt` (The public key used by everyone to verify other certificates).
*   **CA Key:** `CA.key` (The private key used by the CA to sign new certificates. **This is the most sensitive file in the cluster**).
