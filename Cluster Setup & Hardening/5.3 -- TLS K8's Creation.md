# 🛠️ 5.3 -- TLS Kubernetes Certificate Creation

This lesson provides a practical, step-by-step guide to generating the certificates required for a secure Kubernetes cluster using **OpenSSL**. We will walk through the creation of the Root CA, followed by the client certificates for users and the server certificates for core cluster components.

---

## 🏛️ 1. Generating the Certificate Authority (CA)

The CA is the "Root of Trust" for the entire cluster. Every other certificate in the cluster must be signed by this CA to be considered valid.

### The Process:
1.  **Generate Private Key:** Create a secure key that only the CA possesses.
2.  **Create CSR:** Create a Certificate Signing Request with the Common Name (CN) `KUBERNETES-CA`.
3.  **Self-Sign:** Since the CA is the root, it signs its own certificate.

### 💻 Implementation:
```bash
# Generate the CA private key
openssl genrsa -out ca.key 2048

# Create the Certificate Signing Request (CSR)
openssl req -new -key ca.key -subj "/CN=KUBERNETES-CA" -out ca.csr

# Self-sign the CA certificate
openssl x509 -req -in ca.csr -signkey ca.key -out ca.crt
```
**Result:** You now have `ca.crt` (Public) and `ca.key` (Private).

---

## 👤 2. Generating Client Certificates

Client certificates allow users and internal components (Scheduler, Controller Manager) to authenticate themselves to the Kube API Server.

### Admin User Certificate
For the administrator, we generate a key, a CSR with the CN `kube-admin`, and then sign it using the CA created in the previous step.

```bash
# Generate private key
openssl genrsa -out admin.key 2048

# Create CSR
openssl req -new -key admin.key -subj "/CN=kube-admin" -out admin.csr

# Sign the certificate using the CA
openssl x509 -req -in admin.csr -CA ca.crt -CAkey ca.key -out admin.crt
```

> [!TIP]
> **Granting Admin Privileges:** To ensure the user has administrative rights, include the group `system:masters` in the Organizational Unit (OU) field:
> ```bash
> openssl req -new -key admin.key -subj "/CN=kube-admin/O=system:masters" -out admin.csr
> ```

### 🧪 Testing the Client Certificate
You can use these certificates to make a direct REST API call to the Kubernetes API server:

```bash
curl https://kube-apiserver:6443/api/v1/pods \
  --key admin.key --cert admin.crt --cacert ca.crt
```
**Expected Response:** A JSON object listing the pods in the cluster.

## 🖥️ 3. Generating Server-Side Certificates

Server certificates prove the identity of the component providing the service.

### A. etcd Server Certificate
The etcd server is the cluster's source of truth and must be highly secure. It often uses both server certificates and peer certificates for inter-node communication.

**Example etcd configuration (`etcd.yaml`):**
```yaml
etcd:
  --advertise-client-urls=https://127.0.0.1:2379
  --key-file=/path-to-certs/etcdserver.key
  --cert-file=/path-to-certs/etcdserver.crt
  --client-cert-auth=true
  --data-dir=/var/lib/etcd
  --initial-advertise-peer-urls=https://127.0.0.1:2380
  --initial-cluster=master=https://127.0.0.1:2380
  --listen-client-urls=https://127.0.0.1:2379
  --listen-peer-urls=https://127.0.0.1:2380
  --name=master
  --peer-cert-file=/path-to-certs/etcdpeer1.crt
  --peer-client-cert-auth=true
  --peer-key-file=/path-to/etcd/peer.key
  --peer-trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
  --snapshot-count=10000
  --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
```

### B. Kube API Server Certificate
The API Server is accessed via multiple DNS names and IPs. Therefore, we must use **Subject Alternative Names (SANs)**.

**1. Generate Key and CSR:**
```bash
openssl req -new -key apiserver.key -subj "/CN=kube-apiserver" -out apiserver.csr
```

**2. Create OpenSSL Config (`openssl.cnf`) for SANs:**
```ini
[req]
req_extensions = v3_req
distinguished_name = req_distinguished_name

[ v3_req ]
basicConstraints = CA:FALSE
keyUsage = nonRepudiation
subjectAltName = @alt_names

[alt_names]
DNS.1 = kubernetes
DNS.2 = kubernetes.default
DNS.3 = kubernetes.default.svc
DNS.4 = kubernetes.default.svc.cluster.local
IP.1 = 10.96.0.1
IP.2 = 172.17.0.87
```

**3. Sign the Certificate:**
Sign the `apiserver.csr` using the `ca.crt` and `ca.key`.

### C. Kubelet Server and Client Certificates
Each node runs a kubelet which acts as a mini-HTTPS server.
*   **Kubelet Server Cert:** Validates the identity of the node.
*   **Kubelet Client Cert:** Used by the kubelet to authenticate with the API server. These usually follow the naming convention `system:node:<node-name>`.

## 🔄 Summary of the Process

| Component | File Type | Key Detail | Purpose |
| :--- | :--- | :--- | :--- |
| **CA** | `ca.crt`, `ca.key` | Root of Trust | Signs all other certs |
| **Admin** | `admin.crt`, `admin.key` | `O=system:masters` | Full cluster control |
| **etcd** | `etcdserver.crt`, `.key` | Server Cert | Secure state storage |
| **API Server**| `apiserver.crt`, `.key` | SANs (DNS/IP) | Secure entry point |
| **Kubelet** | `kubelet.crt`, `.key` | `system:node:<name>` | Node-to-API auth |
