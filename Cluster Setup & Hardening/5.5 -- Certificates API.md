# 📜 5.5 -- Certificates API

Welcome to the lesson on managing certificates and exploring the **Kubernetes Certificates API**. In this guide, you will learn how Kubernetes automates certificate signing and rotation, and how this integrates into the overall security of the cluster.

---

## 🎓 Introduction to Certificate Management

In a secure Kubernetes cluster, the **Certificate Authority (CA)** is the root of trust. Initially, administrators use the CA to generate certificates for core components. However, as the cluster grows and more administrators join the team, manual signing becomes inefficient.

### The Manual Workflow (Legacy)
When a new administrator needs access:
1.  The user generates a **Private Key** and a **Certificate Signing Request (CSR)**.
2.  The user sends the CSR to the cluster administrator.
3.  The administrator uses the CA server's private key and root certificate to sign the CSR.
4.  The administrator returns the signed certificate to the user.

> [!WARNING]
> **The CA Server is Critical:** The CA server consists of a key and certificate file that can sign certificates for the **entire cluster**. Unauthorized access to these files allows an attacker to grant themselves any privilege within the environment. These files must be strictly secured.

In `kubeadm` deployments, these CA files are typically stored on the master node.

---

## 🚀 Automating with the Certificates API

To handle growth and scale, Kubernetes provides a built-in **Certificates API**. This allows administrators to manage CSRs as Kubernetes objects, moving the process from the command line of the master node to the API server.

Instead of manual signing, administrators create a `CertificateSigningRequest` object. This makes CSRs visible, reviewable, and manageable via `kubectl`.

## 🛠️ Step-by-Step Implementation

Here is the exact workflow for using the Certificates API to onboard a new user (e.g., Jane).

### Step 1: Generate a Private Key and CSR
The user creates their own identity locally.

```bash
# Generate the private key
openssl genrsa -out jane.key 2048

# Generate the Certificate Signing Request (CSR)
openssl req -new -key jane.key -subj "/CN=jane" -out jane.csr
```

The resulting `jane.csr` looks like this:
```text
-----BEGIN CERTIFICATE REQUEST-----
MIICWDCCCAAwE...dhk
-----END CERTIFICATE REQUEST-----
```

### Step 2: Submit the CSR to the Administrator
The administrator creates a `CertificateSigningRequest` object. The CSR must be **Base64-encoded** before being placed in the manifest.

**Example Manifest:**
```yaml
apiVersion: certificates.k8s.io/v1beta1
kind: CertificateSigningRequest
metadata:
  name: jane
spec:
  groups:
  - system:authenticated
  usages:
  - digital signature
  - key encipherment
  - server auth
  request: <base64-encoded-CSR>
```

### Step 3: Review Pending CSRs
The administrator checks for any pending requests:

```bash
kubectl get csr
```
**Example Output:**
```text
NAME   AGE   REQUESTOR           CONDITION
jane   10m   admin@example.com   Pending
```

### Step 4: Approve the CSR
After verifying the identity, the administrator approves the request:

```bash
kubectl certificate approve jane
```
Kubernetes now signs the certificate using the CA key pair.

### Step 5: Retrieve the Signed Certificate
The administrator extracts the signed certificate from the CSR object:

```bash
kubectl get csr jane -o yaml
```

The signed certificate is found in the `status.certificate` field as a Base64 string.

**Example of a signed CSR object:**

## ⚙️ Certificate Management in the Control Plane

The actual "work" of signing and approving certificates is handled by the **Kube Controller Manager**.

![Kubernetes Architecture Components](https://kodekloud.com/kk-media/image/upload/v1752871346/notes-assets/images/Certified-Kubernetes-Security-Specialist-CKS-Certificates-API/frame_330.jpg)

Specifically, the Controller Manager runs internal controllers dedicated to **CSR-Approving** and **CSR-Signing**.

![Controller Manager Functions](https://kodekloud.com/kk-media/image/upload/v1752871347/notes-assets/images/Certified-Kubernetes-Security-Specialist-CKS-Certificates-API/frame_340.jpg)

### Controller Manager Configuration
To perform these tasks, the Controller Manager must have access to the CA's root certificate and private key. This is configured via flags:

**Configuration Excerpt:**
```yaml
spec:
  containers:
    - command:
      - kube-controller-manager
      - --address=127.0.0.1
      - --cluster-signing-cert-file=/etc/kubernetes/pki/ca.crt
      - --cluster-signing-key-file=/etc/kubernetes/pki/ca.key
      - --controllers=*,bootstrapsigner,tokencleaner
      - --kubeconfig=/etc/kubernetes/controller-manager.conf
      - --leader-elect=true
      - --root-ca-file=/etc/kubernetes/pki/ca.crt
      - --service-account-private-key-file=/etc/kubernetes/pki/sa.key
      - --use-service-account-credentials=true
```
